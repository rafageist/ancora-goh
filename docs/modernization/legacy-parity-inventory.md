# Legacy responsibility inventory: academic and scheduling domain (#70)

Issue: #70, under #66. This is a research and documentation deliverable. No product code changes. No legacy code changes.

**Rule of this document.** The maintainer ruled on 2026-10-25 (#70, #66) that **the legacy implementation is the functional specification**. Every row below records what the legacy code *does*, not what it should do. A row's "Target" keeps that semantics in the Drupal/engine replacement. Where the legacy behaviour looks like a defect, it is listed under [Legacy quirks to keep visible](#legacy-quirks-to-keep-visible). Fixing such a defect needs its own explicit approval. Where sources conflict, the conflict is one narrow question under [Genuine ambiguities](#genuine-ambiguities).

## How to read the rows

- **Source.** Paths are repo-relative.
  - `B` marks a file of the frozen LBR baseline `dev/lbr/baseline.tsv` (revision 1, on master).
  - The `pre-drupal-cut` set (`dev/lbr/sets/pre-drupal-cut/baseline.tsv`, revision 2) is not on master yet. It exists only on branch `feat/issue-67-lbr-sets` (commit `c5fede5`).
  - Both sets use the same repo-relative path key (`path<TAB>stream<TAB>component<TAB>bytes<TAB>blob`). In both sets the generated code is counted once, through its generator, and has no rows of its own: `model/**`, `control/data/**`, `control/view/**`, `view/{combo,grid,gallery}/**`. Generated handlers below are therefore cited without `B`.
  - Hand-written handlers (`control/custom/**`), templates (`view/custom/**`), client code (`www/js/app/**`) and `dev/sql/**` are baseline files.
  - Every blob under `control/`, `view/` and `www/js/app/` in the pre-drupal-cut set matches the current HEAD.
- **Observed.** Behaviour read in the code or verified by a probe.
  - "Verified (case NNN)" means a characterization case in `dev/sql/tests/cases/` asserts it.
  - "Probe" means it was run once in the ephemeral cluster for this inventory.
  - **[2010]** marks behaviour of the July 2010 snapshot (`b42aa03`) where the recovered code differs because of an approved fix (#14, #22, #23, #24, #35, #44, D-01).
- **MPI/Prioriza.** Whether `generar()`, `and_mpi()`/`posible_inicio()` or the Prioriza ordering read the data, and how.
- **Drupal today.** The state on master after #85, #86 and #89:
  - **Equivalent**: same observable behaviour. "Engine" means the unchanged legacy SQL engine does it, and Drupal only has to feed it.
  - **Deviation (Dn)**: Drupal behaves differently.
  - **Missing (Dn)**: Drupal has no equivalent.
  - D1–D9 are the deviations acknowledged in #70. D10–D15 are new ones found here; they are not the SQL decision ids `D-01`…`D-10` of `sql-reconciliation.md`.
- **Char. test.** ✔ NNN means a case exists. **new NNN** means this inventory added the case (all `expect: pass`, recorded below). Otherwise the row names the scenario that is still needed. "HTTP" means the behaviour lives in PHP and needs the differential harness (the next step in #70).
- **Target.** Where the legacy semantics go: a Drupal entity, field, constraint or service, or the engine.

Drupal paths are abbreviated as follows: `A/` = `modern/web/modules/custom/ancora_academic/src/`, `S/` = `.../ancora_scheduling/src/`, `E/` = `.../ancora_engine/src/`.

### Public timetable viewer: proposal for #62 (not implemented)

The Drupal viewer is for logged-in users only. Nothing switches anonymous access on: there is no setting, and the route requires a login even if the anonymous role is given the permission (`ViewerTest::testAnonymousDenied`). If #62 approves public timetables, this is the proposed shape, for approval, not a release:

- A site setting `ancora_scheduling.viewer.anonymous`, default **off**, changed only by a site administrator with config deployment, never by a query parameter, header or form of the viewer. With it on, the route would drop the login requirement for the anonymous role and nothing else.
- The legacy semantics raise policy questions that the code cannot answer, so they need a decision before any public mode:
  1. **Consent.** Legacy publishes every user's timetables at once. Which plans may be published, and who decides: each planner per plan, or the organization's administrator for the site?
  2. **Personal data.** Teacher names and the brigade tree are visible to anyone. Should a public mode show teacher names, or codes only?
  3. **Drafts.** Should draft placements (partial runs) be public, or only final timetables?
  4. **Scope.** One site is one organization (the tenant boundary is the site database). Should publication be per site only, or could an organization publish a subset of its plans?
  5. **Caching.** Anonymous pages would enter the page cache; the viewer's cache contexts (`user`, `user.roles:authenticated`, the query arguments) and the placements' list cache tags would have to be checked against the page cache before any release.
