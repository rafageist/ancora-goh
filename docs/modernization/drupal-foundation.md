# Drupal 11 foundation (issue #69)

Issue: #69, under the replatforming decision #66. Áncora GOH is rebuilt as a Drupal 11 application in `modern/`. This document covers the Composer project, its settings and secrets, the install procedure, the tests and the upgrade policy. It also lists what this foundation deliberately leaves to later issues.

The legacy code stays where it is. Moving it under `legacy/` is #68, after the comprehensive LBR cut (#67).

## Versions

| Component | Version | Notes |
| --- | --- | --- |
| Drupal core | **11.4.11** (`drupal/core-recommended` ^11.4, locked) | The production host runs 11.4.10 for the studio site. Same minor release line. |
| Drush | 13.8.0 (`drush/drush` ^13.6) | |
| PHP | ^8.4 | Tested on 8.4 (local) and 8.5 (CI). The production host runs 8.5. Composer resolves for `config.platform.php = 8.4.0`, so the lock installs on both. |
| PostgreSQL | 16 and 18 | Tested on 16 (local) and 18 (CI). The production host runs 18. Drupal needs the `pg_trgm` extension in the site database. |
| Test tooling | `drupal/core-dev` 11.4.11 (dev only) | PHPUnit 11.5, drupal/coder 8.3 (phpcs Drupal + DrupalPractice), Mink, PHPStan |

**Contrib modules: none.** The foundation uses only Drupal core: Entity/Field API, Views, Forms, Twig, Single Directory Components, Configuration Management, users, roles and permissions. A contrib module will be added only when it brings clear value and is covered by the Drupal security advisory policy.

## Layout

```
modern/
  composer.json, composer.lock   project definition and exact dependency versions
  config/sync/                    exported site configuration (source of truth for installs)
  settings/ancora.settings.php    environment-driven settings shared by every site
  scripts/install-disposable.sh   install from scratch + every test, in a disposable cluster
  scripts/http-smoke.sh           HTTP smoke test of an installed site (loopback only)
  phpcs.xml.dist, phpunit.xml.dist
  web/                            web root (document root of the web server)
    sites/default/settings.php    committed; no secrets; includes ../settings/ancora.settings.php
    modules/custom/ancora/        the Áncora module
    themes/custom/ancora_theme/   the Áncora theme
  vendor/, web/core/, ...         generated by composer install; never committed
  private/                        default private files directory; never committed
```

Only first-party files are tracked. `modern/.gitignore` whitelists the web root: core, contrib, the scaffold files (`index.php`, `.htaccess`, `robots.txt`, ...), `settings.local.php`, `files/` and the test directories are ignored. The `artifact` job in CI fails if a vendor, core, contrib, files, dump or `settings.local.php` path is ever tracked.

The configuration sync directory, the shared settings file and the private files directory are all outside the web root.

## Settings, environment and secrets

`web/sites/default/settings.php` contains no secret and no host-specific value. It sets an environment variable prefix (`ANCORA_`) and includes `settings/ancora.settings.php`. Every value comes from the environment. Every secret comes from a file named by a `*_FILE` variable, never from the variable itself.

| Variable | Required | Default | Meaning |
| --- | --- | --- | --- |
| `ANCORA_ENVIRONMENT` | no | `production` | `production`, `development` or `testing` |
| `ANCORA_DB_HOST` | no | `localhost` | Host name, IP address or Unix socket directory |
| `ANCORA_DB_PORT` | no | `5432` | |
| `ANCORA_DB_NAME` | **yes** | | Database name |
| `ANCORA_DB_USER` | **yes** | | Database role |
| `ANCORA_DB_PASSWORD_FILE` | no | | File holding the password. Leave it unset for peer or trust authentication over a socket. |
| `ANCORA_HASH_SALT_FILE` | **yes** | | File holding a random salt (at least 32 random bytes) |
| `ANCORA_TRUSTED_HOSTS` | in production | | Comma-separated host names. Each is matched literally (anchored, escaped). |
| `ANCORA_CONFIG_SYNC_DIR` | no | `modern/config/sync` | |
| `ANCORA_PRIVATE_PATH` | no | `modern/private` | Private files directory |
| `ANCORA_TMP_PATH` | no | system default | Temporary directory |
| `ANCORA_REVERSE_PROXY_ADDRESSES` | no | | Comma-separated proxy IPs, for example `127.0.0.1` behind a local Caddy |

**Fail closed.** A missing database name, user or hash salt, an unreadable secret file, an unknown environment, or (in production) missing trusted hosts throws an exception. The site never falls back to the interactive installer. That matters on a public host: an exposed `install.php` with no database settings would let anyone install the site.

**Security defaults.** These apply in every environment:

- `update_free_access` and `allow_authorize_operations` are `FALSE`.
- In production, errors are never displayed (`display_errors=0` and `system.logging.error_level = hide`, as a settings override, so it is not exported to configuration).
- `skip_permissions_hardening` is never set. Drupal keeps `sites/default` read-only.
- Entity update backups are on.
- `trusted_host_patterns` is required in production.

Development relaxations go in `web/sites/default/settings.local.php`. That file is git-ignored and is included last if it exists. It must never be deployed.

**Under PHP-FPM**, pass the variables with `env[ANCORA_...] = ...` entries in the pool, or keep `clear_env = no` with a systemd `EnvironmentFile`. Keep secret files outside the code tree: mode `0640`, owned by root, group the pool user (see `docs/saas/host-assessment.md`, section 3).

**Multisite (#72).** The shared settings file is site-neutral. Organization sites (`web/sites/org-<slug>`, served at `/o/<slug>/`) include it through `settings/ancora.org.settings.php` and read their database, salt and files from a per-site file outside the web root. See [`drupal-multisite.md`](drupal-multisite.md).

## Configuration management

**Approach: the committed `config/sync` is the source of truth. Every install uses `drush site:install --existing-config`.**

- `scripts/install-disposable.sh` (default mode) installs from `config/sync`. It then exports the configuration of the fresh site to a temporary directory and requires it to be **identical** to `config/sync` (`diff -r`). An install that does not reproduce the committed configuration fails.
- `scripts/install-disposable.sh --bootstrap` rebuilds `config/sync` from scratch. Maintainers run it only when the base configuration has to change. The steps are:
  1. Minimal profile, site time zone UTC.
  2. Enable `ancora`, `ancora_theme` and `claro`.
  3. Default theme `ancora_theme`, admin theme `claro`.
  4. Empty update notification e-mail list.
  5. Uninstall `stark`.
  6. Export.

  Review the resulting diff like any code change.
- Configuration owned by the module (for example the Views listing) lives in `ancora/config/install` and is also part of the export.
- The site UUID is fixed by `config/sync/system.site.yml`. Every installation from it is the same site for configuration purposes.

## Install

Requirements: PHP 8.4+ with `pdo_pgsql`, `gd`, `mbstring`, `xml`, `curl`; Composer 2; PostgreSQL 16+ server binaries. Docker is not needed.

```sh
# From the repository root: install from scratch into a disposable cluster and run every test.
dev/sql/tools/with-ephemeral-pg.sh modern/scripts/install-disposable.sh

# Install only, and keep a 127.0.0.1 server for manual inspection
# (the path of the admin password file is printed, the password never is).
dev/sql/tools/with-ephemeral-pg.sh modern/scripts/install-disposable.sh --skip-tests --keep-server
```

The script never connects to a persistent server. It first calls `agoh_require_disposable` from `dev/sql/tools/disposable-guard.sh`, then performs these steps:

1. Creates the `ancora` role (LOGIN, random password), the `ancora` and `ancora_test` databases owned by it, and `pg_trgm` in both.
2. Writes the database password, the hash salt and the admin password to `0600` files in a temporary directory.
3. Runs `composer install` (skip with `--skip-composer`) and `drush site:install --existing-config`.
4. Sets the admin password from its file. Drush only ever sees a throwaway password, so no log shows a usable one.
5. Runs the configuration determinism check, phpcs, PHPUnit and the HTTP smoke test.

It deletes everything temporary on exit. The cluster itself is deleted by `with-ephemeral-pg.sh`.

**Measured on the development workstation** (PHP 8.4.27, PostgreSQL 16.15, vendor already installed):

| Step | Time |
| --- | --- |
| Site install from `config/sync` | about 4 s |
| Full run: install, determinism check, phpcs, PHPUnit, HTTP smoke | about 30 s |
| `--bootstrap` install (minimal profile, then modules, themes and export) | about 11 s |
| `composer install` from an empty cache | 1 to 2 minutes |

## The `ancora` module and the `ancora_theme` theme

Both are deliberately small. They prove the platform, not the domain model (#70).

### Module (`web/modules/custom/ancora`, PSR-4 namespace `Drupal\ancora`)

**Status route.** `/ancora/status` (`ancora.status`) requires the permission `view ancora status`.

- The controller uses constructor autowiring.
- It returns a `#theme => ancora_status` render array: core version, PHP version, database driver and version, and the academic term count.
- The cache contexts and tags are set (`user.permissions`, `ancora_academic_term_list`).
- The hook is an OOP `#[Hook('theme')]` implementation. The module has no `.module` file.

**Entity type `ancora_academic_term`.** It is defined with the PHP attribute `#[ContentEntityType]`.

- Base fields: name, unique code, first day and last day (date-only `datetime`), created, changed.
- The entity-level constraint `AncoraAcademicTermDates` requires that the last day is not before the first day. It applies to forms, Drush and any future API.
- Handlers:
  - an access handler: `view ancora academic terms` to view; the `administer ancora academic terms` admin permission, marked restricted, for everything else;
  - a list builder at `/admin/content/ancora-term`;
  - a content entity form, with add, edit and delete;
  - `AdminHtmlRouteProvider` routes;
  - Views data.

**Views proof.** `views.view.ancora_academic_terms` is a table page at `/ancora/terms`, protected by `view ancora academic terms`.

### Theme (`web/themes/custom/ancora_theme`)

- `base theme: false`, with `enforce_prop_schemas: true`.
- One page template, two small CSS files using custom properties and light/dark colours. No JavaScript.
- The **`status-card` Single Directory Component** has a schema-validated `heading` and `items`. The theme's override of the module's `ancora-status.html.twig` renders the status page with it, so the module stays presentation-neutral.
- Claro is the administration theme.

## Tests

| Check | Where | Result on the workstation (PHP 8.4, PG 16) |
| --- | --- | --- |
| `composer validate --strict` | CI | valid |
| `composer audit` (locked, all and `--no-dev`) | CI | no advisories |
| phpcs, Drupal + DrupalPractice (custom module, theme, settings) | script, CI | 29 files, 0 errors, 0 warnings |
| PHPUnit Kernel: `AcademicTermTest` (4), `StatusPageTest` (2) | script, CI | 6 tests pass |
| PHPUnit Functional: `FoundationTest` (2), built-in server on 127.0.0.1 | script, CI | 2 tests pass (8 tests, 99 assertions in total) |
| Configuration determinism (export equals `config/sync`) | script, CI | 86 files identical |
| HTTP smoke test (`scripts/http-smoke.sh`) | script, CI | 17 checks pass |

The HTTP smoke test checks:

- the front page and its security headers;
- that no PHP error text is shown;
- the status route, the term administration and the term listing: all `403` for anonymous;
- that a wrong password is refused;
- the administrator login, with the password posted from its file;
- the status page rendered by the component;
- adding a term through the real form, with its CSRF token;
- the term appearing in the list builder and in the Views page.

**PHPUnit and a socket-only database.** The disposable cluster has no TCP listener, and Drupal's `SIMPLETEST_DB` URL cannot name a Unix socket directory as the PostgreSQL host. The test base classes `AncoraKernelTestBase` and `AncoraBrowserTestBase` substitute the host of the parsed URL with `ANCORA_TEST_DB_SOCKET_DIR` when that variable is set. Nothing else changes, and without the variable they behave exactly like the core base classes.

**CI** (`.github/workflows/modern.yml`) has two jobs:

- **`drupal`**: a matrix of PHP 8.4 and 8.5 × PostgreSQL 16 and 18. PostgreSQL 18 comes from the PGDG apt repository when the runner lacks it. The job runs `composer validate`, `install` and `audit`, then the full `install-disposable.sh`, with a Composer cache.
- **`artifact`**: checks that no generated or secret path is tracked. It also checks that a `composer install --no-dev` build contains no dev dependency and passes `composer audit --no-dev`.

The existing repository checks keep their scope:

- `dev/ci/php-lint.sh` lints the new tracked PHP files too.
- `dev/ci/php84-check.sh`, the legacy PHP 4/5 static checker, now excludes `modern/`, like `portal/` and `dev/codegen/`.

## Upgrade policy

- **Core.** Follow the supported Drupal 11 minor line. Apply patch and security releases promptly with `composer update "drupal/core-*" --with-all-dependencies`, then run `drush updatedb` and `drush config:export` and commit the lock and any configuration change. A new minor release (11.x) is adopted after the CI matrix passes on it. Drupal 12 is planned when it is released and the contrib set (currently empty) supports it.
- **PHP and PostgreSQL.** The CI matrix always contains the production host's versions (currently PHP 8.5 and PostgreSQL 18) and the local development versions.
- **Security.** `composer audit` runs in CI on every change to `modern/`. The `update` core module reports security releases in the status report. Its e-mail recipients are set per deployment, not in `config/sync`.
- **Dev dependencies** (`drupal/core-dev`) follow the core version and are never installed in a production build (`composer install --no-dev`).
